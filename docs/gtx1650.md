# GTX 1650 (TU117, no tensor cores)

A GTX 1650 is compute capability 7.5 but has no tensor cores. The sm_75 kernels run (see
[sm75.md](sm75.md)), but the 4-step SFT DiT needs its distilled LoRA. On a card without tensor cores,
runtime LoRAs were previously force-merged into the INT8 ConvRot block weights; requantizing 252
adapters this way visibly destroys the image (a regular dot lattice, banded background and wrong
detail) even though the INT8 GEMMs are bit-exact and the VAE round trip is clean.

## Runtime LoRA side branch (this branch)

Instead of merging, sm_75 now runs the LoRA as a side branch without tensor cores:

- `SideBranches` uploads A as fp16 (the bf16-linear GEMM path) and B as fp32; `t` stays fp32.
- `compute_t` uses the fp16 cuBLASLt GEMM; the small-K delta GEMM uses cuBLASLt's fp32 path, which is ~4.5x faster
  on this GPU (1.46-1.59 vs 0.29-0.33 TFLOPS), and converts its fp32 output once to bf16.
- The base INT8 ConvRot GEMM is unchanged (bit-exact CUTLASS sm_75 MMA).
- The low-rank Δ is added to the base GEMM's bf16 output in fp32 by a SIMT epilogue
  (`kernels/sm75/lora_sm75.cu`), then the site's own `gated_residual`/`situ_glu` epilogue runs
  (`models/moss_dit/dit_block_quant.cpp`).
- `force_lora_merge_on_sm7x()` no longer overrides the requested placement, so `--lora-placement
  side_branch` (and the default) work on Turing.

No offline conversion is needed: use the original INT8 DiT and the runtime LoRA:

```sh
moss-infer generate --model <bundle> --dit moss_image_sft_int8_convrot.safetensors \
  --tier high --lora moss_image_sft_4step_v2.0.safetensors --lora-scale 1.0 \
  --lora-placement side_branch --attention exact \
  --prompt "best quality, highres, a red apple on a wooden table soft light" \
  --steps 4 --cfg 1 --shift 5 --seed 42 -o out.png
```

Verified on a GTX 1650 4 GiB at 256²: image matches the official reference (stem, water droplets,
clean background), with the same ~3.5 s/step as the old merge path. `q8_fp16` attention is refused on
this GPU (no tensor cores); unset attention resolves to exact. See [sm75.md](sm75.md).
